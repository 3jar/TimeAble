# TimeAble 기획서 — 프레임워크 & 웹앱 기반 설계 원리

> 2026-11-11 · 발표용 초안. 나중에 팀 기획서(team_plan)에 통합.

## 1. 왜 "웹앱"인가 — 서비스 성격과의 정합

TimeAble의 목표는 **과제 결과물 + 캠퍼스 바이럴**이다. 이 성격이 플랫폼을 결정한다.

- **설치 장벽 0**: 링크 하나로 즉시 접근. 앱스토어 심사·설치 없이 "목요일 호수 보러 와" → URL 공유로 끝.
- **공유가 곧 기능**: 포스터 이미지·링크 공유가 핵심 동기(기획안). URL 중심 모델 = 웹 네이티브.
- **크로스 플랫폼 무료**: 모바일·데스크톱 브라우저 한 벌로 커버.

→ 네이티브 앱이 아니라 **웹앱(SPA)** 으로 가는 이유는 "접근성과 공유가 서비스의 본질"이기 때문이다.

## 2. 기술 스택 전경 — 3-tier 분리

| 계층 | 프레임워크 | 플랫폼 | 역할 |
|---|---|---|---|
| 프론트 | **Next.js + three.js** | Vercel | 복셀 지형 렌더, 상호작용, 캐싱·계산 |
| 백엔드 | **FastAPI** (Python/uv) | Render | 시간표 import·연동, (권위적) 계산 |
| 데이터 | **Supabase** (Postgres·Auth·Realtime) | Supabase | 저장·인증·실시간 |

**왜 이 조합인가**
- **Next.js**: SPA + SSR 선택지, Vercel 네이티브 배포, three.js와 자연스러운 통합.
- **three.js**: 복셀을 `InstancedMesh`로 수천 블록도 가볍게(기획안). 30분 격자 = 블록 1:1.
- **FastAPI**: 계산 중심 API·Pydantic 검증·자동 OpenAPI·async. 시간표 파싱/연동이 Python 생태계(기존 `timeable` 패키지).
- **Supabase**: Auth·DB·Realtime을 한 번에. 프론트가 직접 붙을 수 있어 백엔드를 얇게 유지.

## 3. 분리 배포 원리 — 한 덩어리가 아닌 이유

```
web/  (순수 Next.js) ──→ Vercel          물리적으로 다른 폴더 + 다른 플랫폼
src/timeable/ (Python) ─→ Render     →   빌드 충돌이 "구조적으로 불가능"
Supabase (매니지드)                      전부 무료 티어 → 비용 0
```

- 세 조각을 각자 잘하는 매니지드 플랫폼에 올린다. 폴더 레이아웃은 안 바꾼다.
- **주의**: Render 무료 티어는 유휴 15분 후 슬립(콜드스타트) → 발표 직전 1회 깨우기. FastAPI엔 `CORSMiddleware`로 Vercel 도메인 허용.

## 4. 핵심 원리 — "쓰기 경로"와 "읽기 경로"의 분리

웹앱 설계의 심장. 두 경로의 **빈도와 무게가 정반대**라 다르게 다룬다.

```
[쓰기 · 드묾 · 무거움]
  시간표 import  →  FastAPI(로그인·파싱)  →  Supabase(members.busy 저장)
     학기당 몇 번

[읽기 · 빈번 · 가벼움]
  그룹 격자 fetch(1회)  →  클라 캐시  →  브라우저에서 지형/수위 즉석 계산
     슬라이더 움직일 때마다 · 네트워크 0
```

→ **무거운 일은 가끔(import), 가벼운 상호작용은 즉석(client)**. 이게 웹앱 기반의 가장 큰 이득이다.

## 5. 웹앱의 장점을 살린 클라이언트 캐싱·계산

**(a) 캐싱 사다리**

| 계층 | 수단 | 효과 |
|---|---|---|
| 인메모리 | React Query/SWR, Zustand | 탭 사는 동안 재사용, 네트워크 0 |
| 영속 | IndexedDB / localStorage | 새로고침·재방문 즉시 로드 |
| 전송 | `Cache-Control` + `ETag` | 네트워크 가도 304로 저렴 |

그룹 격자는 작다(20명×5×24 bool ≈ 수 KB) → 클라에 들고 있기에 이상적.

**(b) 파생 계산을 브라우저에서**

`free_counts`/`handler`는 작은 격자 위 카운팅이라 **JS로 포팅**하면, 수위 슬라이더가 움직일 때마다 **수 ms 즉석 재계산 · 서버 호출 0**. 지형 감상이 오프라인급으로 즉각 반응한다.

**(c) 무효화(가장 어려운 부분)**
- `groups.updated_at`(version)으로 "격자가 바뀌었나" 판정
- **stale-while-revalidate**: 캐시로 **즉시 그리고**, 뒤에서 조용히 재검증
- 실시간 반영은 **Supabase Realtime** 푸시("이 그룹 멤버 바뀜") → 해당 클라만 refetch

**(d) 트레이드오프**
클라 계산을 쓰면 availability 알고리즘이 **Python+JS 두 벌**이 된다 → **클라 계산 주도**, Python `handler`는 import 파이프라인·검증·테스트용 권위본으로 유지.

## 6. 상태·세션 원리

- **백엔드는 stateless**: 세션은 Supabase/클라가 들고, FastAPI는 **JWT 검증만**.
- 단 하나의 예외: **import 진행중 OTP 상태**는 상주 서버(Render) 인메모리로 잠깐 유지(OTP suspend/resume). 서버리스였으면 불가능했을 지점.

## 7. 렌더링 원리 (three.js)

- `InstancedMesh`로 블록 수천 개를 한 draw call에 — 복셀 1:1 격자, 보간 없는 선명한 시간 경계.
- **정사영 아이소메트릭 고정** → 디오라마 느낌 + 포스터 내보내기 동일 각도.
- 클라 계산이 만든 **지형 필드(수위별 높이/인원)** → GPU 인스턴싱 입력.

## 8. 한 줄 원리 모음

- 서버는 **얇게**(JWT·import·권위 계산), 클라는 **똑똑하게**(캐시·즉석 계산), 저장은 **Supabase**.
- **무거운 건 드물게, 가벼운 건 즉석.**
- 분리 배포로 **빌드 충돌 0, 비용 0**.
